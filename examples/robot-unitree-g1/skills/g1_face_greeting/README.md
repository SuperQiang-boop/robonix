# G1 Face Greeting

This skill consumes confirmed encounter events from `face_recognition`. It is the only owner of greeting speech and intimacy-selected arm actions.

The G1 manifest enables `ROBONIX_GREETING_STATE_PATH` at `${ROBONIX_DEPLOY_DIR}/data/greeting_state.json`. With `navigation_enabled: true`, this opts into Planner coordination: the skill publishes atomic greeting facts, confirms stopping, greets and asks “有什么可以帮助您的吗？”, waits for estimated playback and confirmed arm release, then opens one 15-second Gateway voice capture on `g1_audio`. Voice authorization remains in Gateway. The request uses the interrupted Executor plan's exact session; multiple navigation owners or missing session metadata are rejected. The full voice stream is drained after task admission, without submitting the transcript a second time. No speech means Planner may continue the original paused task. A new temporary request is handled by Planner's `cancel_plan` with `resume_after: true`, then fresh planning of the original unfinished work after verified success. This skill never resumes navigation itself in this mode. Without the environment variable, the existing pause/greet/resume behavior below remains in use.

Rebuild/restart Planner, Executor, Gateway, navigation and this skill together before using coordination. Planner keeps retained tasks in session memory; a process restart does not automatically restart them. The local snapshot restricts navigation admission, queued dispatch and resume even after the original run is cancelled. Missing/malformed state, failed release or uncertain voice admission keeps navigation inhibited. After an interrupted greeting restart, verify physical stopping and controller release before removing the stale snapshot and reactivating the skill. Stop invalidates late voice requests for that session and encounter; it does not skip arm cleanup. Playback is still estimated, not measured audio completion. External RViz/manual movement bypasses this service and must remain excluded during greeting trials.

Offline checks: run `rbnx-build/venv/bin/python -B -m unittest discover -s tests`; after building the Rust services, run `rbnx-build/venv/bin/python -B tests/smoke_task_handoff.py`. The latter starts isolated local Src/Executor/Planner processes and a deterministic model, and verifies A→B→A, greeting hold, temporary-task failure, replacement and Stop using harmless shell markers. It does not drive hardware or measure actual ASR/TTS/model language accuracy.

`ARM_GREETING_ENABLED` in `g1_face_greeting/main.py` is set to `True` for the navigation comparison with arm greetings restored. Speech and the selected arm action run in parallel, and confirmed arm release is required before navigation resumes. Set the constant to `False` and restart this skill to repeat the speech-only trial: it opens no arm connection and sends no arm action or release request, while retaining navigation stop, playback wait and fresh stationary odometry checks. In speech-only mode, the response has `action: ""` and `action_ok: false` because no arm action was attempted; the detail records that it was skipped. The following arm-action and release requirements apply when the constant is `True`.

With `navigation_enabled: true`, recognized encounters pause the active navigation run and wait up to 8 seconds for fresh stationary odometry before speech and arm actions. After the greeting wait, even when speech or the preset failed, the skill calls `release_arm`. Resume requires confirmed release feedback, a still-paused run and fresh stationary odometry; it retains the original run ID and destination. Greeting errors remain in the response and logs even when navigation resumes. Missing release feedback, stale odometry, user cancellation, unexpected greeting exceptions or skill shutdown prevents automatic resume. Cleanup still attempts release after a greeting exception or shutdown during the wait. Without an active navigation run, this mode also greets recognized people after the navigation service confirms fresh stationary odometry and no queued, paused or active goals. Speech and arm failures still lead to an arm release attempt; failures remain in the result/logs. There is no navigation resume call in this case. Nav2 must remain online even when idle. Active RViz goals are observed and cannot authorize this idle branch. Manual motion and new external goals must not run concurrently with greetings. Turning remains disabled.

`navigation_provider_id` defaults to `nav2`. `greeting_wait_sec` defaults to 12 seconds measured from greeting start using a monotonic clock; longer speech waits at least text length / 3 seconds. Speech and arm calls run in parallel and count toward this interval. After both calls return, only the remaining interval is waited before releasing the arm; a call taking longer than the interval adds no further playback wait. Logs report elapsed, remaining and total estimated playback seconds. This estimates playback completion and must be verified on the target robot. Rebuild `packages/g1_arm` and reload its primitive as well as this skill: an older arm helper only reports acceptance and cannot authorize resume. The release helper requires new `rt/arm/action/state` feedback received after the release request starts (`id=99`, `holding=false`), including feedback arriving before the RPC reply. It also accepts this G1 firmware's sustained `id=0`, `holding=false`, `name=""` feedback after SDK success (at least three samples over 0.2 seconds, fresh within 0.3 seconds). Both forms confirm controller release, not measured joint position. Reload this skill as well as rebuilding the arm helper when updating idle-feedback compatibility. Navigation checks fresh healthy G1 chassis diagnostics separately from measured odometry, which remains available for display after a motion fault. Rebuild the chassis daemon and adapter and reload navigation together before enabling trials. Rebuild/reload both navigation and this skill for idle greetings; keep `navigation_enabled: true`, with no additional config required. The default false mode remains stationary-only and does not check motion.

Intimacy is supplied by the face service. The default action mapping is:

- levels 1-2: `wave_under_head`
- level 3: `wave_above_head`
- level 4: `make_heart_with_right_hand`
- level 5: `make_heart_with_both_hands`

Build with `bash scripts/build.sh`, which creates a package venv containing FastMCP's HTTP client support, then add this package to the deployment manifest after `face_recognition`, speech, and `g1_arm_actions`. The build intentionally pins MCP to major version 1 and FastMCP to major version 3 because the service and skill use the MCP v1 server API. The virtualenv must be rebuilt if it still resolves incompatible pre-existing packages.

Run the package smoke tests with `rbnx-build/venv/bin/python -m unittest discover -s tests` from this package directory. They cover both arm modes and verify that speech-only navigation waits for stopping and playback, sends no arm requests, and does not resume after cancellation, stale odometry, or shutdown. Hardware playback and SDK transport still require an on-robot trial.

Planner can call `create_message` with an exact registered `person_name`, verbatim `message`, and `sender` (empty string if unspecified). This ordinary-message capability only resolves the person through `face_recognition/people/resolve` and never calls Scene. It then stores a one-time task bound to the registered person ID. `list_messages`, `message_status`, and `cancel_message` query or cancel tasks by ID. Multiple pending messages to the same person are spoken together during the next observed encounter, combined with the normal greeting in one speech request while the arm action starts in parallel. Greeting cooldown does not suppress a pending message. A prior buffered face event cannot deliver a message created later.

Creation is idempotent for an identical pending target, sender, message, and tracked object: repeated Planner/tool calls return the original `task_id` instead of creating another task. Whitespace and terminal punctuation differences are ignored for this deduplication check. A task that is already `delivered` is not deduplicated, so a later explicit request can intentionally send the same words again.

For the minimal object handoff flow, call the separate `create_object_message` capability with `object_label`, for example `cup`. Only this capability calls `robonix/system/world/list_objects`, requires exactly one current object with that label, and stores its stable Scene `object_id` in the task. It does not infer relations such as "on the stool" and does not track by label after creation. `message_status` calls World again only for tasks created through `create_object_message` and reports `object_status`: `present` when that ID is still listed, `removed` when World no longer lists it, and `unknown` when World cannot be queried. Under the current agreed assumption, `removed` means the object was taken away. A missing/temporarily unavailable World response is never treated as removal.

Example Planner request:

```text
我把杯子放在机器人面前了。下次见到小B时，告诉他小C让他把杯子拿走。
```

Planner should call `create_object_message` with `person_name: 小B`, the spoken `message`, `sender: 小C`, and `object_label: cup`. After the encounter, a follow-up query for the task status refreshes the cup state before answering whether it remains in front of the robot. For an ordinary message, call `create_message` and do not query Scene first.

Set `message_store_path` in the deployment manifest to an absolute persistent SQLite path (the example uses `${ROBONIX_DEPLOY_DIR}/data/face_messages.sqlite3`, outside `rbnx-build`). Keep the skill activated after task creation so it continues consuming face events; a restart requires activation again. Task states are `pending`, `delivering`, `delivered`, `uncertain`, and `cancelled`. `delivered` means only that the speech service returned success; speech errors or restart during delivery become `uncertain` and are **not** automatically repeated. A task already being delivered cannot be cancelled. No unsolicited Planner notification is sent; users can query task status. Task creation is limited to 160 characters per message and 180 combined pending message/sender characters per recipient, to keep one speech request bounded. The stationary-only mode must not be activated while navigating.
